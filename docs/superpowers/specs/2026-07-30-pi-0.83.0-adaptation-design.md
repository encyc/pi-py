# pi v0.83.0 适配设计

## 背景

`pi-py` 当前对齐 `earendil-works/pi@v0.82.1`，并有意定位为 Python SDK：
保留 `pi-ai`、agent runtime、编码工具 SDK、SQLite storage 和 server，
不复刻上游 CLI/TUI、OAuth、扩展系统和未支持的 provider。

上游 v0.83.0 对当前 Python 已支持范围有四类有效变化：

1. 流式消息新增中间停止状态 `pending`。
2. 最终消息保留 provider 原始停止原因 `rawStopReason`，未知或缺失的终止原因不再视为成功。
3. 支持按请求注入 HTTP 传输实现。
4. OpenAI-compatible 流同时携带有效 `function` 和空 `custom` 时，不得丢失函数参数。

上游 TypeBox 升级、OAuth、凭证导出、OpenRouter 登录、GitHub Copilot 模型、
图片 provider 及 coding-agent CLI/TUI 修复不在本轮范围内。

## 目标

- 将现有 OpenAI、Anthropic 和 Faux provider 的停止原因语义对齐到 v0.83.0。
- 保留 provider 原始停止原因，以便调用方诊断兼容端点。
- 将上游 `fetch` 注入能力映射为 Python SDK 原生异步 HTTP client 注入。
- 修复 OpenAI-compatible malformed tool-call delta 的参数丢失。
- 将五个 Python 包及同步元数据统一升级到 0.83.0。
- 使用单元测试、静态检查以及 DeepSeek、OpenCode Zen 真实调用证明适配有效。

## 非目标

- 不新增 Google、Mistral、Bedrock、OpenAI Responses、图片或 OAuth provider。
- 不实现 `pi auth`、OpenRouter 登录、扩展上下文或模型目录更新。
- 不引入 CLI/TUI、扩展系统或完整上游 `AgentSession`。
- 不为了字面对齐 TypeScript `fetch` 而创建 fetch-to-httpx 适配层。
- 不做与 v0.83.0 适配无关的重构。

## 公共 API 设计

### 停止原因

`StopReason` 增加 `"pending"`。`AssistantMessage.stop_reason` 的生命周期为：

1. provider 建立流时初始化为 `"pending"`；
2. provider 收到明确终止原因后映射为 `"stop"`、`"length"`、`"toolUse"`、
   `"error"` 或 `"aborted"`；
3. 流结束时若仍为 `"pending"`，以 provider error 结束，不能发布成功的 `done` 事件。

`AssistantMessage` 增加：

```python
raw_stop_reason: str | None = Field(default=None, alias="rawStopReason")
```

OpenAI 和 Anthropic 在收到非空终止原因时先保存原始值，再执行统一映射。
Faux 用于验证公共契约；它没有外部 provider 原始值，因此默认保持 `None`。

### HTTP client 注入

`StreamOptions` 增加：

```python
http_client: Any = Field(default=None, alias="httpClient", exclude=True)
```

该对象必须是目标 provider Python SDK 接受的异步 HTTP client。OpenAI 和 Anthropic
client 构造器把它原样传给各自 SDK 的 `http_client` 参数。

这是对上游 `fetch` 的有意 Python 化映射：

- 不公开名为 `fetch` 的 Python 参数；
- 不改变默认网络行为；
- `stream_simple` 与 `stream` 使用同一注入路径；
- client 生命周期由调用方管理，provider 不主动关闭外部注入对象；
- `PORTING.md` 明确记录这一命名差异。

## Provider 行为

### OpenAI-compatible

- 输出消息初始 `stop_reason` 为 `"pending"`。
- 每次遇到非空 `finish_reason`，保存为 `raw_stop_reason` 并映射统一原因。
- 没有 `finish_reason`、映射后仍为 `pending` 或映射为 `error` 时，以 error 事件结束。
- 未知终止原因必须成为 provider error，错误信息包含原始原因。
- tool-call delta 同时包含 `function` 和 `custom` 时，以 `function` 为准。
  只有不存在 `function` 时，`custom` 才进入 grammar tool 输入路径。
- 注入的 `http_client` 传给 `AsyncOpenAI`。

### Anthropic

- 输出消息初始 `stop_reason` 为 `"pending"`。
- `message_delta.stop_reason` 非空时保存原始值并映射统一原因。
- 流结束仍为 `pending` 时，以 error 事件结束。
- safety 或未知原因不得被误判为正常停止，错误信息包含原始原因。
- 注入的 `http_client` 传给 `AsyncAnthropic`。

### Faux

- 流式 partial 消息从 `pending` 开始。
- 测试脚本若提供最终 `pending` 消息，必须失败，避免自定义 provider 复制错误模式。
- 正常脚本继续按文本或工具调用生成最终 `stop` 或 `toolUse`。

## Agent、Storage 与 Server

`pi-agent-core`、`pi-coding-agent`、`pi-storage-sqlite` 和 `pi-server`
没有需要移植的 v0.83.0 运行时代码。它们只进行：

- 包版本升级到 `0.83.0`；
- workspace 内部依赖更新为 `>=0.83.0,<0.84`；
- `__version__` 和 `__upstream_ref__` 更新；
- smoke tests、README、PORTING、CHANGELOG、SYNC 和 `UPSTREAM_VERSION` 更新。

现有 agent loop 继续消费统一 `AssistantMessage.stop_reason`，无需感知原始停止原因。

## 错误处理

- provider 的异常继续遵循现有契约：编码为 `ErrorEvent` 并以错误消息结束 EventStream，
  不从后台驱动任务泄漏未处理异常。
- 缺失终止原因使用明确错误：
  - OpenAI-compatible：`Stream ended without finish_reason`
  - Anthropic：`Anthropic stream ended without a stop reason`
- 未知 provider 终止原因的消息必须包含原始值。
- HTTP client 类型不在 `StreamOptions` 构造时强校验，由 provider SDK 报告不兼容对象；
  这保留各 SDK 支持的 client 子类和测试 double。
- 真实集成测试不得打印、持久化或提交 API key。

## 测试设计

### 单元测试

`pi-ai` 增加或更新以下回归覆盖：

- `StopReason`/`AssistantMessage` 接受 `pending` 和 `rawStopReason` 的序列化往返；
- OpenAI 流在开始事件中呈现 `pending`；
- OpenAI 保存原始 `finish_reason` 并正确映射；
- OpenAI 缺失或未知 `finish_reason` 返回 error；
- OpenAI 的有效 `function` 与空 `custom` 共存时保留函数参数；
- OpenAI client 构造收到注入的 `http_client`；
- Anthropic 流在开始事件中呈现 `pending`；
- Anthropic 保存原始 stop reason，缺失或未知原因返回 error；
- Anthropic client 构造收到注入的 `http_client`；
- Faux partial 使用 `pending`，最终 `pending` 被拒绝。

现有五个包的 smoke tests 更新为精确断言 `0.83.0` 和
`earendil-works/pi@v0.83.0`。

### 本地质量门

必须通过：

```bash
uv run pytest
uv run ruff check
uv run ruff format --check
uv run mypy
```

### 真实 provider 验证

使用现有本地凭证，至少执行：

- DeepSeek：普通流式文本、工具调用、pi-agent-core agent loop；
- OpenCode Zen：通过其现有 OpenAI-compatible endpoint 执行普通流式文本和工具调用；
- 两者的最终消息均不得停留在 `pending`；
- 两者在 provider 返回终止原因时均应填充 `raw_stop_reason`。

OpenCode Zen 的 endpoint、model 和凭证从现有本地配置解析。若解析遇到问题，
必须继续检查项目配置和本机现有 pi/OpenCode 配置；仍无法解析时报告具体阻塞，
不能把该项静默记为通过或宣称适配完成。
